# KnowledgeDock — Deployment Setup (Render free + MongoDB Atlas free + Gemini free)

Target infrastructure, in the order you must do it:

```text
1. MongoDB Atlas   → gives MONGODB_URI
2. Google AI Studio → gives GEMINI_API_KEY
3. GitHub          → gives Render something to build
4. Render          → hosts the app, holds secrets
```

Nothing in `.env` is committed. You copy values into Render's dashboard by hand.

---

# Part A — MongoDB Atlas (free M0 cluster)

## A1. Open Atlas and create a project

1. Go to `https://cloud.mongodb.com`.
2. Click **Sign In** and sign in with a Google account (same one is fine).
3. On first login Atlas asks for an **organisation**. Enter any name, e.g.
   `badhan-personal`. Click **Create Organisation**.
4. Atlas switches to **Project** screen. Click **Create Project**.
5. Project Name: `knowledgedock`. Click **Next**.
6. Click **Create Project**. Your project opens with a dashboard showing no
   clusters yet.

## A2. Create the free M0 cluster

1. Atlas shows a big green button **Create Deployment**. Click it.
2. A page titled *Deploy a Cluster* opens. Under **Shared** (the free tier,
   labelled `M0 FREE`), click **Create**.
3. Fill the form:
   - **Cloud Provider**: `AWS`
   - **Region**: pick the one closest to your Render region. Use this mapping:

```text
Render Oregon     → Atlas  Oregon     (us-west-2)
Render Virginia   → Atlas  Virginia   (us-east-1)
Render Ohio       → Atlas  Ohio       (us-east-2)
Render Frankfurt  → Atlas  Frankfurt  (eu-central-1)
Render Singapore  → Atlas  Singapore  (ap-southeast-1)
```

Keep the two in the **same** region. `$vectorSearch` is an aggregation
pipeline, so one question costs several Atlas round trips; a cross-region
pair puts an ocean in that path, and M0 allows only 100 ops/sec.


   - Leave **Tier**: `M0 FREE`
   - Click **Create Deployment**.
4. Wait 1–3 minutes. The dashboard turns green and shows `M0 FREE` with your
   cluster name (usually `Cluster0`). This is your database.

> M0 facts that constrain the design: 100 database operations per second, and
> a hard limit of **3 Atlas Search/Vector Search indexes** on the whole cluster.
> KnowledgeDock therefore uses exactly **one** vector index, with
> `workspace_id` declared as a `filter` field inside it instead of relying on
> separate indexes. Plain BSON indexes do not count against this limit.

## A3. Create the database user (this is your password)

1. Left sidebar → **Database Access**.
2. Click **Add New Database User** (top right).
3. Fill the form:
   - **Authentication Method**: `Password`
   - **Username**: `knowledgedock`
   - **Password**: click **Autogenerate Secure Password**. Atlas shows it ONCE.
     Copy it into your password manager immediately — you cannot read it again.
   - **Database User Privileges**: choose
     `Read and write to any database`
4. Click **Add User**.

> **Important:** do not use the autogenerated password. It contains characters
> like `/`, `@`, `#` that must be URL-encoded inside a MongoDB connection string,
> and forgetting to encode them produces a confusing authentication error.
> Instead click **Autogenerate** → **Provide Your Own Password**, and set a
> password of 20+ characters using only `A-Z a-z 0-9`. Example shape:
> `KdM0ngoAtlas9fR2x7LpQa` (make up your own — never copy this one).

## A4. Open network access

Render's free tier does **not** have static outbound IP addresses, so Atlas
cannot be locked to a single IP.

1. Left sidebar → **Network Access**.
2. Click **Add IP Address**.
3. Click **ALLOW ACCESS FROM ANYWHERE**. Atlas fills in `0.0.0.0/0`.
4. Click **Confirm**.

> Atlas will warn that this allows connections from any IP. This is expected and
> unavoidable on Render's free tier. Security comes from: strong Atlas
> credentials, argon2id password hashing in the app, JWT auth on every
> endpoint, and rate limiting (Phase 8). If you later upgrade to a paid Render
> plan, come back here and replace `0.0.0.0/0` with Render's static egress IPs.

## A5. Copy the connection string

1. Left sidebar → **Deployment** (or click the green `Connect` button on the
   cluster card in the dashboard).
2. A **Connect a window** modal appears. Click the **Drivers** tab.
3. Driver dropdown: choose **Node.js**. Do not pick PyMongo — Atlas does not
   have a Python driver template, but the SRV string it gives you is identical
   for every driver.
4. Copy the string at the bottom. It looks like:

```text
mongodb+srv://knowledgedock:<db_password>@knowledgedock.xxxxx.mongodb.net/?retryWrites=true&w=majority
```

5. Replace `<db_password>` with the password you chose in A3.
6. Put the finished value into your local `.env` as `MONGODB_URI`. The query
   string at the end (`?retryWrites=true&w=majority`) is fine to keep.

## A6. Verify it works before deploying anything

The repository ships a check for this. It reads your `.env` and uses the same
driver the application uses, so a pass means the container path is the path the
app will take:

```bash
uv run python scripts/check_mongo.py
```

Exit codes: `0` reachable, `1` connection failed, `2` a required variable is
missing from `.env`.

If it prints `{'ok': 1.0}` the credentials, network access and DNS are all
correct. If it fails:

| Error | Cause |
|---|---|
| `ServerSelectionTimeoutError` | Network Access not set to `0.0.0.0/0`, or cluster still provisioning |
| `Authentication failed` | Wrong password, or unencoded special characters |
| `bad auth : Authentication failed` with weird chars | Password contains `@ : / # ?` — recreate with alphanumeric only |

# Part B — Gemini API key (free tier)

## B1. Open Google AI Studio

1. Go to `https://aistudio.google.com`.
2. Click **Sign in** with your Google account.
3. Accept the terms if prompted.

## B2. Pick or create a project

1. At the top left there is a project dropdown showing
   `Get a code snippet` / an unnamed project.
2. Click the dropdown → **Create project**.
3. Project name: `knowledgedock`. Click **Create**.
4. Wait for it to be created and selected.

You can skip this — AI Studio auto-creates a project for you — but having your
own named project makes the API key easier to find and revoke later.

## B3. Create the API key

1. Left sidebar → **Get API key** (in newer UIs it is just **API keys**).
2. Click **Create API key**.
3. A dialog appears with an **API Key** field. Name it `knowledgedock-render`.
4. Click **Create**.
5. A popup shows the key. It starts with `AIza` and ends with 35 characters.
   Click **Copy**.
6. Paste it into your local `.env` as `GEMINI_API_KEY`. Do not paste it into
   any file inside the repository.

## B4. Restrict the key (do this)

1. Still on the **API keys** page, find `knowledgedock-render`.
2. Click the **⋮** (three dots) menu → **Edit**.
3. Under **API restrictions**, set **Restrict key** to
   `Generative Language API`.
4. Under **Application restrictions**, leave it empty for now (IP restrictions
   would break once Render assigns a dynamic egress IP).
5. Click **Save**.

This means a leaked key can only call Gemini — it cannot touch any other Google
service.

## B5. Verify the key works

Open a terminal and run:

```bash
export GEMINI_API_KEY='AIza...your-key...'
curl -s "https://generativelanguage.googleapis.com/v1beta/models/gemini-3.8-flash:generateContent?key=$GEMINI_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"contents":[{"parts":[{"text":"say OK"}]}]}'
```

If you get JSON containing `"text": "OK"`, the key is good.

If you get:

| Error | Cause |
|---|---|
| `API key not valid` | Key was deleted or you copied it wrong |
| `403` | Free tier not available in your country — check Google's supported regions |
| `429 RESOURCE_EXHAUSTED` | Free-tier quota for that model exhausted; try again after the daily reset |

## B6. Know your free quota

Gemini's free tier (no billing enabled) allows only Flash-class models:

```text
gemini-3.8-flash        free tier, Flash class
gemini-embedding-001    free tier
Pro-series models       PAID ONLY since April 2026
```

Free-tier limits are per model and Google revises them without notice. Read the
authoritative numbers for your project at
`https://aistudio.google.com` -> **Dashboard** -> **Usage**, and remember the
quota is shared by every request your app makes. KnowledgeDock makes one chat
call per question and one embedding call per batch of chunks, so budget uploads
accordingly.

Check your live quota at `https://aistudio.google.com` → **Dashboard** →
**Usage**. Never click **Set up billing**, or the app starts costing you money
on day one.

> Free-tier prompts and responses may be used by Google to improve its
> products. Do not upload confidential documents into a free-tier demo.

# Part D — Create the Render web service

## D1. Create the service

1. Go to `https://dashboard.render.com`.
2. Left sidebar → **New** → **Web Service**.
3. **Connect** a GitHub repository. Authorise Render for your account, then
   pick `knowledgedock`.
4. Fill the form:

| Field | Value |
|---|---|
| Name | `knowledgedock` |
| Branch | `main` |
| Language / Runtime | `Docker` |
| Dockerfile Path | `./Dockerfile` |
| Docker Context | `.` (leave blank) |
| Region | same as the Atlas region you chose in A2 |
| Instance Type | `Free` |

5. Do not click **Create Web Service** yet — set the env vars first.

## D2. Set environment variables

Scroll to **Environment Variables**. Click **Add Environment Variable** once per
line from your local `.env`.

`SECRET_KEY`, `MONGODB_URI` and `GEMINI_API_KEY` are the only three values you
must fill in. Everything else in `.env.sample` already carries a working
default.

**Never set these on Render — they are platform-provided or container-only:**

```text
PORT          Render injects 10000 itself
STORAGE_DIR   must stay /tmp/knowledgedock/uploads inside the container
```

**Fill in these three, marking each as `SECRET`:**

| Key | Value | Mark as Secret |
|---|---|---|
| `SECRET_KEY` | output of `openssl rand -base64 48` | yes |
| `MONGODB_URI` | from A5 | yes |
| `GEMINI_API_KEY` | from B3 | yes |

Bulk import is the fast path: copy `.env.sample` to `.env`, fill in the three
secrets, then in Render choose **Add from .env** and paste the whole file.
Render creates all 36 keys in one go. Go back afterwards and confirm
`SECRET_KEY`, `MONGODB_URI` and `GEMINI_API_KEY` show as secret rather than
plain text. There are no email or admin-bootstrap variables — Phase 2 creates
the first account through registration.

**Generate SECRET_KEY locally, never on the Render UI:**

```bash
openssl rand -base64 48
```

## D3. Set the health check path

1. Scroll to **Advanced**.
2. **Health Check Path**: `/health`
   (`/healthz` answers identically — the app serves both — but `/health` is
   the name used everywhere else in this project.)
3. Make sure **Docker Command** is **empty**. The `CMD` in the Dockerfile is
   used. If you set it, the exact value is:
   `sh -c "uvicorn knowledgedock.main:app --host 0.0.0.0 --port ${PORT:-8000} --proxy-headers --forwarded-allow-ips='*'"`

## D4. Create and deploy

1. Click **Create Web Service**.
2. Render starts a build. Watch progress under **Events**.
3. When it finishes, Render prints your URL:
   `https://knowledgedock.onrender.com`
4. Open `https://knowledgedock.onrender.com/health`. You should get
   `{"status":"ok"}`.

# Part E — What the first deploy can and cannot prove

Phase 1 is merged on `main`, so `src/` exists and the image builds. The deployed
service answers:

```text
GET /            -> 200  Bootstrap shell
GET /health      -> 200  {"status":"ok"}
GET /health/ready-> 503 or 200, depending on Atlas reachability
GET /static/*    -> 200
```

This is enough to prove the whole delivery pipeline before any business logic
exists: Docker builds, the container binds `0.0.0.0:$PORT`, Render's port scanner
and health check pass, and `/health/ready` proves the Atlas credentials and
network path work from inside the container.

It proves nothing about authentication, documents, ingestion, retrieval or RAG.
Those land in Phases 2–7 and each one gets its own roadmap checkbox.

**Order matters.** Create the Render service and set every variable from
`.env.sample` *before* the first build. The application validates its
configuration at import time and exits with `MissingConfigurationError` naming
the offending variable, so a partial environment fails the deploy loudly rather
than starting in a broken state.

# Part F — Operating notes for the free tier

## F1. Cold starts

Free web services **spin down after 15 minutes without traffic**. The next
request takes roughly one minute while Render shows a loading page. Nothing is
broken; this is expected. A document caught mid-processing when the instance
sleeps is requeued on the next startup, because the worker treats every
`PROCESSING` row it finds at startup as abandoned — on a single worker, nothing
else could have claimed it.

## F2. Ephemeral filesystem

Uploads under `/tmp/knowledgedock/uploads` are wiped on every redeploy, restart
and spin-down. This is acceptable: the text is extracted once at upload time and
the extracted text, chunks and vectors live in Atlas, so the worker re-embeds
from the stored text even when the disk is gone. The raw file is only a staging
artefact. Free Render services cannot have a persistent disk.

## F3. Monthly limits

```text
750 free instance hours per month, per workspace
5 GB outbound bandwidth per month included
```

One always-on service uses ~744 hours/month, so a single service is fine but a
second one will exhaust the quota. Track usage at
`https://dashboard.render.com/billing`.

## F4. Ports

Render scans `0.0.0.0:10000` by default. Ports `18012`, `18013` and `19099`
are reserved. The Dockerfile's `CMD` reads `${PORT}` and binds `0.0.0.0`, which
satisfies Render's port scanner.

## F5. Secret hygiene

```text
.env                      stays on your machine, already git-ignored
.env.sample               committed, no secrets
Render dashboard          only place the real values live
uv.lock, pyproject.toml   committed, no secrets
```

If a secret ever leaks:

1. Rotate it at the source — Atlas (database access → user → edit password),
   AI Studio (API keys → delete), or locally for `SECRET_KEY`.
2. Update the matching variable in Render.
3. Click **Save Changes** → Render redeploys.
4. `SECRET_KEY` rotation logs everyone out. That is expected and safe.

# Part G — Build troubleshooting

## `ERROR: ghcr.io/astral-sh/uv:<tag>: not found`

The build died on the very first `FROM`. The tag does not exist in the registry.
uv renamed its Debian variant: images up to `0.9.30` ship `-bookworm-slim`, and
from `0.10.x` onward the variant is `-trixie-slim`. There is no `bookworm` tag for
modern uv at all.

Check which tags actually exist before pinning:

```bash
curl -s "https://ghcr.io/token?scope=repository:astral-sh/uv:pull&service=ghcr.io" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['token'])" > /tmp/tok
curl -s -H "Authorization: Bearer $(cat /tmp/tok)" \
  "https://ghcr.io/v2/astral-sh/uv/tags/list?n=1000" \
  | python3 -c "import sys,json; print([t for t in json.load(sys.stdin)['tags'] if '0.11' in t and 'python3.12' in t])"
```

Note the registry returns at most 1000 tags per page. If a version you expect is
absent, page through with the `Link: rel="next"` header before concluding it does
not exist.

Verify a `FROM` line resolves without running a build:

```bash
python3 - <<'EOF'
import json, urllib.request
repo, tag = "astral-sh/uv", "0.11.16-python3.12-trixie-slim"
tok = json.load(urllib.request.urlopen(
    f"https://ghcr.io/token?scope=repository:{repo}:pull&service=ghcr.io"))["token"]
req = urllib.request.Request(f"https://ghcr.io/v2/{repo}/manifests/{tag}", headers={
    "Authorization": f"Bearer {tok}",
    "Accept": "application/vnd.oci.image.index.v1+json,"
              "application/vnd.docker.distribution.manifest.list.v2+json"})
print(json.load(urllib.request.urlopen(req))["manifests"][0]["platform"])
EOF
```

## `exec: "python3.12": executable file not found` or `ModuleNotFoundError` on a C extension

The builder and the runtime were on different Debian releases. Wheels are
resolved against the builder's glibc, and an import-time failure on the older
base is the symptom. Keep `FROM ...-trixie-slim` and `FROM python:3.12-slim-trixie`
on the same release, and keep the same `/usr/local` Python layout so the copied
`.venv` interpreter symlink resolves.

## `chown: invalid group: 'appuser:appuser'`

The runtime user was created without a matching group. `adduser --system` does
not create a same-named group, so `chown user:group` has nothing to resolve
against. The Dockerfile now creates both explicitly with `groupadd`/`useradd`
and a named `--gid`.

## `adduser: command not found` / `useradd: command not found`

Neither binary is present. Debian splits these into the `adduser` and `passwd`
packages and slim images carry a minimal set. Install them first:

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends adduser passwd \
    && rm -rf /var/lib/apt/lists/*
```

## `"/src": not found`

`src/` was not in the build context. Check `.dockerignore` does not exclude it,
and that the code is committed — Render builds the pushed commit, not your
working tree.

## `MissingConfigurationError: <VARIABLE> is not set`

The container started but configuration was incomplete. Render serves variables
from the dashboard; a variable that is absent there but present in `.env.sample`
will stop startup. See `.env.sample` for the full list.

# Part H — Verification checklist

Run through this once after the first successful deploy.

```text
[x] /health       200  {"status":"ok"}
[x] /healthz      200  {"status":"ok"}
[x] /readyz       200  {"status":"ready","database":"up"}
[x] /health/ready 200  {"status":"ready","database":"up"}
[x] /             200  Bootstrap shell
[x] /api/docs     404  production flag in effect, schema not published
[x] Render logs show "Application startup complete" with no traceback
[x] SECRET_KEY / MONGODB_URI / GEMINI_API_KEY marked secret in the dashboard
[x] .env untracked; no secret present in git history
```

All verified against `https://knowledgedock.onrender.com`. `/readyz` returning
`database: up` is the one that matters — it is the only check that exercises
Atlas credentials, TLS and Network Access from inside the container.

If `/health` is 200 but `/health/ready` is 503, the container is fine and Atlas
is not reachable. Read the `mongodb.ping_failed` log line: a
`ServerSelectionTimeoutError` means Network Access is not `0.0.0.0/0`, and
`Authentication failed` means the password in `MONGODB_URI` is wrong.
